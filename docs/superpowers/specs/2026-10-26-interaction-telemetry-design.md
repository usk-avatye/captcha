# SDK 상호작용 계측 설계

날짜: 2026-10-26
상태: 구현 전 검토안

## 목적과 합의한 범위

광고 전환을 개선하기 위해 퍼즐의 첫 조작 시간, 풀이 시간, 실패 횟수와 드래그 경로 표본을 수집한다. 기존 인증 서버와 PostgreSQL을 사용한다. 포인트 샘플과 예약 서비스에 같은 SDK 기능을 적용한다. 시연 시나리오를 구분하는 DB 필드는 추가하지 않는다.

사용자가 선택한 범위는 요약 계측과 드래그 경로 표본을 함께 구현하는 것이다. 아래의 시간 정의, 표본 비율, 저장 형식과 제한값은 구현 제안이다.

## 검토한 접근

1. 요약 계측: 시간 두 개와 실패 횟수만 수집한다. 구현과 저장 비용이 작고 전체적인 사용성을 비교할 수 있다.
2. 요약 계측과 경로 표본: 요약값에 제한된 좌표 표본을 더해 실제 조작을 확인한다. 사용자가 이 범위의 포함을 선택했다.
3. 외부 분석 서비스: 전송과 분석을 제품에 맡기는 방식이다. 사용자는 지속적인 서비스 비용을 피하고 기존 서버에서 직접 구현하는 방향을 선택했다.

브라우저의 Pointer Events와 performance.now()를 활용한다. 별도 분석 플랫폼이나 녹화 라이브러리 설치는 이번 구현에 필요하지 않다.

## 측정 정의

- 첫 조작 시간: 이미지 준비가 끝나 퍼즐을 조작할 수 있게 된 때부터 램프를 처음 누른 때까지의 활성 시간이다. 조작하지 않은 경우 null이다.
- 풀이 시간: 같은 시작점부터 성공 검증 응답을 받은 때까지의 활성 시간이다. 성공 애니메이션 시간은 제외한다. 성공 응답을 받기 전에는 null이다.
- 실패 횟수: 서버가 passed=false로 응답한 논리적인 드롭 시도의 수다. 요청 재전송을 별도의 드롭으로 세지 않는다. 드래그 취소와 통신 오류도 이 횟수에 포함하지 않는다.
- 활성 시간: 인증 창이 열려 있고 브라우저 문서가 보이는 동안 누적한다. 창을 닫거나 다른 탭으로 이동하면 멈추고, 같은 인증을 다시 열면 이어서 잰다.

측정값은 사용성 분석 자료다. 인증의 성공 판정과 예약 저장 조건은 기존 서버 로직이 담당한다.

## 경로 표본

- 인증 한 건이 시작할 때 표본 포함 여부를 한 번 선택한다. 성공 여부와 관계없이 같은 비율로 선택한다.
- SDK 기본 경로 표본 비율은 1%로 제안한다. 회사 맥북의 시연 설정에서는 경로를 확인할 수 있도록 100%로 설정한다. 이 비율은 DB의 시나리오 구분값으로 저장하지 않는다.
- 계측은 램프를 누르고 이동하고 놓는 구간에 한정한다. 고객사 화면 전체를 녹화하지 않는다.
- 좌표는 퍼즐 영역을 기준으로 0~1로 정규화하고 영역 밖의 좌표는 가장자리로 제한한다. 각 점에 활성 경과 시간과 드래그 시도 번호를 함께 담는다.
- 이동 점은 최소 100ms 간격으로 기록하고, 시작과 끝을 포함해 인증당 최대 100개로 제한한다. 상한에 도달하면 마지막 점을 갱신해 최종 위치를 보존한다.
- 재시도한 드래그는 시도 번호로 구분한다. 경로가 없는 경우와 표본 대상이 아닌 경우는 구분한다.

## SDK 연결과 전송

CaptchaFlow의 인증 수명과 CarPuzzle의 입력 이벤트를 연결하는 작은 계측 모듈을 둔다. 이동 이벤트마다 React 상태를 갱신하거나 서버에 전송하지 않는다. 값은 메모리에서 누적한다.

성공 응답, 인증 창 닫기, 문서 숨김과 페이지 종료 시 누적 스냅샷을 비동기로 보낸다. 같은 시도를 다시 열면 누적 기록과 전송 순번을 유지한다. 종료 시점의 전송은 keepalive를 사용한다. 페이지를 다시 연 뒤 확인할 수 없는 종료 기록은 미확인으로 남긴다.

스냅샷은 인증 ID, 증가하는 revision, firstInteractionMs, solveMs, missCount와 선택적인 path를 포함한다. 한 번의 재전송에서는 같은 스냅샷과 revision을 사용한다. 전송 오류는 인증, 포인트 적립, 광고 링크와 예약 처리를 계속할 수 있도록 처리한다.

SDK의 계측 활성화와 경로 표본 비율은 선택적인 설정으로 제공한다. 설정은 해당 인증 시도 동안 고정한다. 두 시연 화면에는 동일한 계측 기능을 적용한다.

## 서버와 저장

현재 captcha_events는 인증 성공 뒤의 click_id를 참조한다. 이 계약은 유지하고, 인증 ID를 받는 POST /api/interaction-summaries를 추가한다. 따라서 성공 전 종료한 인증도 기록할 수 있다.

기존 DB에 captcha_interaction_summaries 테이블을 추가한다.

| 컬럼 | 용도 |
| --- | --- |
| challenge_id | 기존 인증을 참조하는 기본키 |
| revision | 누적 스냅샷의 순서와 중복 판정 |
| metrics | 시간 두 개, 실패 횟수와 경로 표본을 담는 JSONB |
| received_at | 마지막으로 반영된 서버 수신 시각 |

요약값과 선택적 경로는 인증당 한 행에 저장한다. 사용자 이메일, 예약 제목과 시나리오 구분값을 복제하지 않는다. 처음에는 이 테이블의 추가 분석 인덱스를 만들지 않는다.

서버는 인증 존재 여부와 입력 형식을 확인한다. 숫자에는 유한성, 정수 여부와 상한을 적용하고, 경로는 좌표 범위, 순서, 길이를 검증한다. 최대 전송 본문은 16KiB, 시간 상한은 24시간, 실패 횟수와 드래그 번호 상한은 각각 1000으로 제안한다.

새 revision은 한 트랜잭션에서 반영한다. 동일한 revision의 동일 내용과 과거 revision은 중복 응답으로 처리하고 새 행을 추가하지 않는다. 동일 revision에 다른 내용이 오면 충돌 응답을 보낸다. 먼저 도착한 새 revision이 과거 스냅샷으로 덮이지 않도록 한다. 메모리 저장소와 PostgreSQL 저장소가 같은 계약을 제공한다.

기존 인증 기록, 광고 이벤트, 포인트와 예약 데이터는 그대로 사용한다. BMW 공식 랜딩 주소도 유지한다. 실제 BMW 신청 완료 수집은 별도 연동 범위다.

## 조회와 시연 반영

점검 명령으로 최근 인증의 요약값과 경로 표본을 조회한다. 경로는 로컬 HTML과 SVG로 열어볼 수 있게 내보낸다. 별도 공개 분석 API나 상시 대시보드 서버는 추가하지 않는다.

SDK 패키지를 다시 빌드하고 예약 서비스에 제공하는 tgz를 갱신한다. 두 웹 이미지와 인증 API에 반영한다. DB 마이그레이션은 기존 기록을 유지하면서 새 테이블만 생성한다.

## 검증과 완료 조건

1. 시계를 제어한 SDK 테스트로 첫 누르기, 재시도, 닫기와 재열기, 문서 숨김, 성공 시각과 실패 횟수를 확인한다.
2. 경로의 표본 선택, 기록 간격, 좌표 정규화, 최대 개수와 마지막 점 보존을 확인한다.
3. API 테스트로 성공 전 기록, 중복, 역순 도착, 잘못된 인증 ID, 과도한 크기와 잘못된 숫자를 확인한다.
4. PostgreSQL 마이그레이션과 동시 갱신 계약을 확인한다.
5. 기존 SDK 테스트와 패키지 계약을 확인하고, 두 소비 화면의 빌드를 확인한다.
6. 실행 환경에서 요약과 경로를 조회하고 기존 데이터가 유지되는지 확인한다. 브라우저에서 직접 CAPTCHA를 조작하는 확인은 도구의 별도 확인 규칙을 따른다.

완료 결과에는 변경된 파일, 확인한 테스트와 실제 시연에서 기록을 확인하는 명령을 남긴다.
